## Background & Gap Analysis

The Admin App already has (via v22):
- `admin.email_templates` — template CRUD with categories `auth`, `billing`, `support`, `system`
- `admin.email_send_log` — audit table for sent emails
- `admin.send_test_email()` — logs only; **no actual SMTP dispatch occurs**
- UI in `modules/content/`: Template List, Template Editor, Send Log

The Platform (project-nidus) already has:
- `public.email_configurations` — multi-provider config (SMTP, Resend, SendGrid, Mailgun, AWS SES)
- `public.email_sender_profiles` — per-context From name/email overrides
- Edge Function `send-email` — Deno function that routes to Resend / SendGrid / SMTP
- Edge Function `send-trial-email` — pattern for scheduled/event-driven emails
- Delivery tracking on `public.email_logs` (message_id, opened_at, clicked_at, bounced_at)

**What admin is missing:**
- Real email dispatch (send_test_email is log-only)
- Ability to compose and send templated emails to individual users from the admin UI
- Bulk broadcast campaigns (send to all active subscribers, by plan, by system)
- Automatic event-triggered emails (tester approved, refund processed, subscription cancelled, etc.)
- Delivery status tracking with provider message IDs
- Email analytics (sends/opens/bounces over time)
- Template categories for affiliate, testers, and marketing use cases
- New critical templates: moratorium expiry (v11.0), affiliate commission, subscription cancellation, refund notifications

**Reuse approach:**
- Admin frontend calls the existing Platform `send-email` Edge Function directly (same Supabase project)
- Admin reads provider config from `public.email_configurations` via a new admin RPC (no duplication of config)
- Admin reads sender profiles from `public.email_sender_profiles` via admin RPC
- Admin logs all sends to `admin.email_send_log` (admin-specific audit trail, separate from `public.email_logs`)
- Platform's queue pattern (pending → sent status lifecycle) applied to admin send log

## Architecture

```
Admin UI (email-centre module)
    │
    ├── compose single email
    │     ├── calls admin.queue_email() RPC  →  admin.email_send_log (status=pending)
    │     ├── calls send-email Edge Function → SMTP/Resend/SendGrid
    │     └── calls admin.update_email_send_status() → updates status, message_id
    │
    ├── campaigns (broadcast)
    │     ├── admin.build_campaign_audience()  →  query public.users + subscriptions
    │     ├── admin.email_queue rows per recipient
    │     └── batch: send-email Edge Function per recipient
    │
    └── event triggers
          └── admin frontend code hooks (e.g., after tester_approved action, call trigger_email_event)

Email Provider Config  →  reads public.email_configurations (via admin RPC, no write from admin)
Sender Profiles        →  reads public.email_sender_profiles (via admin RPC)
```

**Why admin logs separately from Platform's `public.email_logs`:**  
Admin-initiated emails need their own audit trail linked to `admin_user_id` for accountability, separate from Platform's system-generated emails. Admins searching send history should only see admin-initiated emails, not Platform's user-facing automated sends.

### 1b. `admin.queue_email()` — Create pending log entry

```sql
CREATE OR REPLACE FUNCTION admin.queue_email(
    p_recipient_email  TEXT,
    p_template_key     TEXT,
    p_subject          TEXT,
    p_body_html        TEXT,
    p_provider         TEXT DEFAULT NULL,
    p_target_system    TEXT DEFAULT NULL,
    p_admin_user_id    UUID DEFAULT NULL,
    p_metadata         JSONB DEFAULT NULL
)
RETURNS UUID  -- returns send log id
LANGUAGE plpgsql SECURITY DEFINER SET search_path = admin, public
AS $$
DECLARE v_admin_id UUID; v_log_id UUID;
BEGIN
    v_admin_id := COALESCE(p_admin_user_id, admin.current_admin_user_id());
    IF NOT admin.check_admin_permission(v_admin_id, 'system.email.send') THEN
        RAISE EXCEPTION 'Permission denied: system.email.send required';
    END IF;
    INSERT INTO admin.email_send_log
        (recipient_email, subject, status, delivery_status, template_key, provider, target_system, initiated_by, metadata, sent_at)
    VALUES
        (p_recipient_email, p_subject, 'pending', 'pending', p_template_key, p_provider, p_target_system, v_admin_id, p_metadata, NOW())
    RETURNING id INTO v_log_id;
    PERFORM admin.log_admin_action(v_admin_id, 'system.email.send', 'email_send_log', v_log_id, NULL, NULL,
        jsonb_build_object('recipient', p_recipient_email, 'template_key', p_template_key));
    RETURN v_log_id;
END;
$$;
```

### 1c. `admin.update_email_send_status()` — Record dispatch result

```sql
CREATE OR REPLACE FUNCTION admin.update_email_send_status(
    p_log_id        UUID,
    p_status        TEXT,  -- 'sent' | 'failed'
    p_message_id    TEXT DEFAULT NULL,
    p_error_message TEXT DEFAULT NULL,
    p_provider      TEXT DEFAULT NULL
)
RETURNS BOOLEAN
LANGUAGE plpgsql SECURITY DEFINER SET search_path = admin, public
AS $$
BEGIN
    UPDATE admin.email_send_log
    SET status          = p_status,
        delivery_status = p_status,
        message_id      = COALESCE(p_message_id, message_id),
        provider        = COALESCE(p_provider, provider),
        error_message   = p_error_message,
        sent_at         = CASE WHEN p_status = 'sent' THEN NOW() ELSE sent_at END
    WHERE id = p_log_id;
    RETURN FOUND;
END;
$$;
```

### 3b. `admin.trigger_email_event()`

Called by admin frontend after completing an admin action (approve tester, process refund, etc.):

```sql
CREATE OR REPLACE FUNCTION admin.trigger_email_event(
    p_event_type      TEXT,
    p_recipient_email TEXT,
    p_context_data    JSONB DEFAULT '{}',
    p_admin_user_id   UUID DEFAULT NULL
)
RETURNS UUID  -- send_log_id (NULL if trigger inactive or delayed)
LANGUAGE plpgsql SECURITY DEFINER SET search_path = admin, public
AS $$
DECLARE
    v_trigger   RECORD;
    v_template  RECORD;
    v_log_id    UUID;
BEGIN
    SELECT * INTO v_trigger FROM admin.email_event_triggers WHERE event_type = p_event_type;
    IF NOT FOUND OR NOT v_trigger.is_active THEN RETURN NULL; END IF;

    SELECT * INTO v_template
    FROM admin.email_templates
    WHERE template_key = v_trigger.template_key AND is_active = TRUE
    LIMIT 1;
    IF NOT FOUND THEN RETURN NULL; END IF;

    -- If delay_hours > 0, queue into email_queue for scheduled dispatch
    -- If delay_hours = 0, queue immediately (status=pending, frontend dispatches)
    v_log_id := admin.queue_email(
        p_recipient_email,
        v_trigger.template_key,
        v_template.subject,
        v_template.body_html,
        NULL, NULL,
        COALESCE(p_admin_user_id, admin.current_admin_user_id()),
        jsonb_build_object('event_type', p_event_type, 'context', p_context_data)
    );
    RETURN v_log_id;
END;
$$;
```

**Integration points** (admin frontend hooks these calls after each action):
| Admin action | Event type | Where |
|---|---|---|
| After tester approved | `tester_approved` | System Testers module |
| After tester rejected | `tester_rejected` | System Testers module |
| After refund approved | `refund_approved` | Subscriptions module |
| After refund rejected | `refund_rejected` | Subscriptions module |
| After subscription cancelled | `subscription_cancelled` | Subscriptions module |
| After affiliate commission processed | `affiliate_commission_paid` | Affiliates module |
| After affiliate approved | `affiliate_welcome` | Affiliates module |

Moratorium expiry warnings (90d/30d/7d) are **scheduled** — a scheduled job or cron Edge Function queries `public.system_testers` where `expires_at` is approaching and calls `trigger_email_event` for each qualifying tester. This cron is configured as a Supabase cron job (pg_cron or Edge Function on schedule).

### ComposeEmailPage — Flow

1. **Step 1 — Template:** Select from `admin.email_templates` dropdown (search by key/name)
2. **Step 2 — Recipient:** Search user by name/email (queries `public.users`) or type email directly
3. **Step 3 — Variables:** Form inputs auto-generated from `template.variables` JSONB array (e.g. `{{first_name}}`, `{{plan_name}}`)
4. **Step 4 — Preview:** Renders HTML with variables substituted, shows final subject line
5. **Send:** Calls `admin.queue_email()` → gets `log_id` → calls `send-email` Edge Function → calls `admin.update_email_send_status(log_id, result)` → shows success toast with provider message_id

## Phase 6 — Moratorium Expiry Cron (Supabase Edge Function)

Since moratorium expiry warnings (90d/30d/7d) are scheduled (not triggered by an admin action), they require a separate scheduler:

**Edge Function:** `supabase/functions/admin-moratorium-cron/index.ts`

```typescript
// For each approaching expiry, calls admin.trigger_email_event() for the correct window
// Uses Supabase service role key; must only be callable internally (not via anon)
```

```sql
SELECT cron.schedule(
    'admin-moratorium-expiry-check',
    '0 9 * * *',
    $$SELECT net.http_post(

);
```

This replaces the need for each moratorium email to be triggered manually by an admin. The Edge Function handles the tester subscription lookup + `trigger_email_event` calls. The send-email Edge Function then dispatches the actual email.

## Key Design Decisions

1. **Reuse send-email Edge Function** — Don't duplicate. Admin frontend calls the same `send-email` Edge Function that Platform uses. Admin logs sends separately in `admin.email_send_log` for admin-specific audit.

2. **No admin-side provider config** — Platform owns `public.email_configurations`. Admin can READ it (via admin RPC with permission check) but should not duplicate or override it. Config changes go through the Platform Settings UI. This keeps one source of truth for email provider credentials.

3. **Dispatch pattern** — Admin frontend is responsible for calling the Edge Function, not the DB. This follows the Platform's established pattern (`send_transactional_email` queues to DB; application layer dispatches). The DB RPC (`admin.queue_email`) creates the pending log entry; the frontend dispatches; the frontend then updates status. This avoids pg_net complexity.

4. **Campaign dispatch is client-side batched** — The admin frontend calls `admin.enqueue_campaign()` to build the queue, then iterates `admin.email_queue` rows in batches (controlled by `email.campaign_batch_size` system setting), calling the Edge Function per recipient. For very large campaigns (>10,000), an Edge Function-based bulk dispatch should be considered in a future iteration.

5. **Event triggers are opt-in on the admin UI side** — `admin.trigger_email_event()` must be explicitly called after each admin action in the relevant module. This is intentional: not all admins want automatic emails on every action. The EventTriggersPage lets admins disable specific triggers if needed.
