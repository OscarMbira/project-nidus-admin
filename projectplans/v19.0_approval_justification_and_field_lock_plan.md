## 0. Requirements (as given)

1. Every approval page/form must have a **mandatory** comments/justification field for the authoriser — recorded for audit, explaining *why* they approved (or rejected) the change.
2. **All other fields must be non-editable** while a record is under approval, so the authoriser can only see the change, not alter the data — approve or reject, with a reason either way.

## 1. What's already in place vs. what's missing

**Already satisfied, mechanically:** `useConfirmAction` (`packages/ui/src/useConfirmAction.jsx`) already blocks confirmation when `requireReason: true` and the textarea is empty/whitespace (`if (state.requireReason && !state.reason?.trim()) return`). Both existing decision entry points already pass `requireReason: true`:
- `RecordLifecycleToolbar.runOperation` (record's own edit page — currently offers **Validate** and **Delete** in the `unauthorised` state)
- `MyApprovalsPage.decide` (`/admin-mgmt/record-governance/my-approvals` — offers **Approve**/**Reject**)

So "no comment, no confirm" already holds everywhere a decision can be made today. Requirement 1 is largely a **labeling and coverage** gap, not a missing mechanism — see gaps below.

**Missing / broken, found while scoping this:**

| Gap | Detail |
|---|---|
| **No Reject on the record's own page** | The record-page toolbar's `unauthorised` actions are `[validate, delete]` — there is no way to reject an edit from that page, only from My Approvals. `delete` is a different, more destructive operation (moves the whole record to `history`, not just discards the pending edit) — using it as a stand-in for reject would be wrong. |
| **Record-page Validate doesn't close the authorisation request** | `RecordLifecycleToolbar`'s Validate calls `admin.transition_record_status('validate', ...)` directly. It does **not** touch `admin.record_authorisation_requests`. If an authoriser validates from the record page instead of My Approvals, the matching request row is left `status = 'pending'` forever — a "ghost" entry that keeps showing up in My Approvals for an already-decided record. |
| **My Approvals has no diff view** | `MyApprovalsPage` lists `table_name` / `record_id` / `level` / `role` / `submitted_at` only — no visibility into what's actually changing. The `PendingChangesDiff` component built in v18.0 is wired only into `RecordLifecyclePanel` (the record's own edit page), not into the queue page. An authoriser using My Approvals today is being asked to "justify" a decision on data they cannot see. |
| **Fields stay fully editable during the pending window** | Confirmed by inspection of all 4 pilot pages (`PlanCatalogFormPage.jsx`, `AffiliateFormPage.jsx`, `PaymentGatewayFormPage.jsx`, cancellation-category modal) — each tracks `record_status` in state and renders `RecordLifecyclePanel`, but nothing disables the surrounding data-entry form. Anyone with edit permission viewing a pending record — maker or checker — can currently still type into fields and hit Save while a decision is outstanding, defeating the "earlier captured field data" guarantee requirement 2 asks for. |

## 2. Decision needed — consolidate to one decision code path

To satisfy both requirements consistently (mandatory comment + no ghost rows + a real Reject everywhere), the two divergent approval code paths need to converge:

**Recommendation:**
- Refactor `admin.process_authoriser_decision`'s body into an internal helper, `admin._apply_authorisation_decision(p_request admin.record_authorisation_requests, p_decision, p_notes, p_admin_user_id)`, containing all the existing any/all level-progression, rejection-cascade, and `transition_record_status` call-out logic unchanged.
- `admin.process_authoriser_decision(request_id, decision, notes)` becomes a thin wrapper: look up the request row by id, call the helper. (My Approvals keeps calling this exactly as today — no frontend change needed there beyond the diff view.)
- New `admin.decide_pending_record(table_name, record_id, decision, notes, admin_user_id)`: looks up the **caller's own** `pending` request row for that `(table_name, record_id)` and calls the same helper. This is what the record's own edit page uses — it doesn't have a `request_id` in scope, only the record it's looking at.
- **Break-glass fallback:** if the caller holds `lifecycle.configure` but has no matching request row (not literally the assigned authoriser — the existing override from `v125`), `decide_pending_record` falls back to calling `transition_record_status(validate|reject, ...)` directly, same as today, but additionally withdraws any stray `waiting`/`pending` request rows for that record so nothing is left dangling regardless of which door was used to decide it.

This guarantees: every decision, from either page, mandatorily requires a comment (both call through `useConfirmAction`), always resolves the matching request row (no ghosts), and both **Approve** and **Reject** are available everywhere — not just Validate/Delete on the record page.

## 3. Frontend changes

**Record's own edit page (`RecordLifecycleToolbar` / `RecordLifecyclePanel`, `packages/ui/src/RecordLifecycle.jsx`):**
- `OPERATIONS_BY_STATUS.unauthorised` becomes `[{ op: 'approve', label: 'Approve', permission: 'lifecycle.authorise' }, { op: 'reject', label: 'Reject', permission: 'lifecycle.authorise', danger: true }, { op: 'delete', label: 'Discard record', permission: 'lifecycle.configure', danger: true }]` — `approve`/`reject` call `decidePendingRecord(tableName, recordId, decision, notes)` (new); `delete` keeps calling `transitionRecordStatus` as today, relabeled to make clear it discards the whole record (not just the pending edit) and stays restricted to `lifecycle.configure`.
- Both `approve` and `reject` keep `requireReason: true` — the modal copy is updated to read "Approval justification (required)" / "Rejection reason (required)" instead of the generic "Reason (required)", per requirement 1's audit-justification intent.

**Field lock-down (all 4 pilot pages):** wrap each page's editable field block in a native `<fieldset disabled={recordStatus === 'unauthorised'}>`. `disabled` on a `<fieldset>` cascades to every descendant input/select/textarea/button automatically — this avoids touching each individual field in `PlanCatalogFormPage.jsx`, `AffiliateFormPage.jsx`, `PaymentGatewayFormPage.jsx`, and the cancellation-category modal one at a time. Pair with a visible ribbon (extending the amber banner already shipped in v18.0 §0): "This record is locked for editing until the pending change is approved or rejected." The Save button sits inside the same `<fieldset>` so it's disabled too.

**My Approvals (`MyApprovalsPage.jsx`):**
- Add an expandable row (or a "View changes" link opening a side panel) rendering `PendingChangesDiff` for that row's `table_name`/`record_id` — reusing the exact component built in v18.0, now surfaced here too so the authoriser can actually see what they're approving before typing a justification.
- Existing Approve/Reject buttons unchanged (already call `processAuthoriserDecision` with `request_id`, already `requireReason: true`) — just relabel the reason prompt the same way as the record page for consistency.

**`packages/shared/src/lifecycleServices.js`:** add `decidePendingRecord(tableName, recordId, decision, notes)` → `rpc('decide_pending_record', { p_table_name, p_record_id, p_decision, p_notes })`.
