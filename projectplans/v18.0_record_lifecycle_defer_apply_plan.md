# v18.0 — Record Lifecycle Defer-Apply & Governance Gate Completion Plan

**Created:** 2026-07-06
**Status:** Complete
**Builds on:** `v15.0_record_lifecycle_management_plan.md` (Complete) — this plan fixes an architectural gap discovered in that system after it shipped.
**Reported by:** User, via two screenshots (`Developer Images/Subscription Authorisation v1.png`, `v2.png`) — editing a subscription plan ("Basic Monthly", $30) sent it to `Unauthorised` status with no visible way to approve it, and the plan vanished from the live public Subscription Preview instead of the previously-approved version staying visible.

---

## 0. Quick fix already shipped (Bug A, partial)

`modules/subscriptions/src/pages/PlanCatalogFormPage.jsx` now:
- Auto-expands the "Record governance & history" `<details>` panel when `record_status === 'unauthorised'` (was collapsed by default, hiding the Validate button).
- Shows an amber "pending edit awaiting approval" banner above it in the same state (updated in v18 to reflect defer-apply: public preview keeps approved values until validation).

This unblocks the immediate "I can't find the approve button" complaint. It does **not** fix the underlying data-model defect (§2) or the authoriser-permission inconsistency (§1) — both are addressed by this plan.

## 1. Decision needed — reconcile the two approval code paths

Two different code paths currently let someone move a record from `unauthorised` → `live`, with different strictness:

| Path | Permission check |
|---|---|
| `RecordLifecycleToolbar`'s **Validate** button (record's own edit page) → `admin.transition_record_status` | Caller holds `lifecycle.authorise` **OR** `lifecycle.configure` — any super_admin/system_admin can click it, regardless of whether they're an assigned authoriser for that table. |
| **My Approvals** page (`/admin-mgmt/record-governance/my-approvals`) → `admin.process_authoriser_decision` | Caller's admin user id must match the specific `authoriser_id` row seeded in `admin.record_authorisers` for that table/level (v118 seeded a named authoriser for `subscription_plans`). |

**Recommendation:** tighten `transition_record_status`'s `validate` operation so it also requires the caller to be an active row in `admin.record_authorisers` for that table (or hold `lifecycle.configure` as a documented break-glass override), so clicking Validate from the record page enforces the same assignment model as My Approvals. Otherwise the maker/checker control seeded in v118 is trivially bypassable from the record's own page.

**Decision (Phase 0):** Adopted recommendation — implemented in `v125_record_lifecycle_authoriser_strictness.sql`.

## 2. Bug B — the real defect: edits apply to the row before approval

`admin.update_subscription_plan` (v98) writes new field values onto the row **immediately**, then — only if governance is active — flips `record_status` to `unauthorised`. `public.get_public_subscription_plans()` filters `record_status = 'live'` only. Net effect: the instant an edit is submitted, the row's live columns already hold the *unapproved* values, and it simultaneously disappears from the public pricing page — instead of the public page continuing to show the last-approved values until the edit is validated.

There is only one physical row per record (Category B design, no `_history` table split — see v15 §2), so once the new values are written there is nothing left to fall back to. This is what the user hit: renaming to "Basic Monthly" / $30 overwrote the live row, then hid it.

## 3. Newly discovered — gap C: 3 of 4 governed tables were never wired to the gate at all

Auditing the other three tables seeded into `admin.record_lifecycle_config` (v101) turned up something not yet in scope of the original bug report:

| Table | Update RPC | Calls `submit_for_authorisation` / sets `record_status`? |
|---|---|---|
| `subscription_plans` | `admin.update_subscription_plan` (v98) | **Yes** — this is the only one, which is why it's the only table where the bug was visible. |
| `affiliates` | `admin.update_affiliate` (v56) | **No** — writes directly, no lifecycle awareness at all. |
| `payment_gateways` | `admin.update_payment_gateway` (v46) | **No** — same. |
| `cancellation_reason_categories` | `admin.admin_upsert_cancellation_category` (v63) | **No** — same. |

So today, assigning authorisers to those three tables (as the admin-mgmt "Authorisers" page lets you do) has **no effect** — edits go live immediately regardless, silently bypassing governance rather than requiring approval. This is arguably worse than Bug B (which at least enforces approval, just with a UX/visibility side effect).

**Decision (Phase 0):** Wire all three RPCs now — implemented in `v127`–`v129`.

## 4. Design — defer-apply via a generic pending-changes table

New table, one row per record with an in-flight edit (mirrors the existing generic `admin.record_authorisation_requests` pattern rather than adding another JSONB column to each of the four governed tables):

```sql
admin.record_pending_changes
  id                    UUID PK
  table_name            TEXT NOT NULL
  record_id             UUID NOT NULL
  root_record_id        UUID NOT NULL
  submission_batch_id   UUID NOT NULL
  previous_status       TEXT NOT NULL   -- record_status captured at submission time, restored on reject
  proposed_changes      JSONB NOT NULL  -- only the columns the submitter actually changed
  submitted_by          UUID REFERENCES admin.admin_users(id)
  submitted_at          TIMESTAMPTZ DEFAULT NOW()
  UNIQUE (table_name, record_id)        -- at most one in-flight edit per record
```

RLS: same posture as `record_authorisation_requests` — visible to the submitter, any assigned authoriser for that table, or `lifecycle.configure`; writes only via the `SECURITY DEFINER` RPCs below.

**Re-submission while already pending:** if an admin edits a record that already has a pending edit, `UNIQUE (table_name, record_id)` means the new submission's `proposed_changes` replaces the old one (`ON CONFLICT ... DO UPDATE`) — last-submitted values win, matching the single-row physical model. Any still-`waiting`/`pending` `record_authorisation_requests` rows from the superseded batch are withdrawn (same pattern already used elsewhere in `process_authoriser_decision` for same-level supersession).

### Function changes

**`admin.submit_for_authorisation`** — gains `p_proposed_changes JSONB DEFAULT NULL`:
- Always upserts `record_pending_changes` first (`previous_status` = current `record_status` before this call), regardless of bypass vs. governed — this means there is exactly **one** merge code path (in `transition_record_status`), not two.
- Governance active (authorisers exist + `approval_enabled`): flips `record_status` to `unauthorised` only — **no other column is touched**. Row keeps its last-approved values for the entire pending window.
- Bypass (no active authorisers / `approval_enabled = false`): immediately calls `transition_record_status(..., 'validate', ...)` as today, which now also performs the merge (see below) — so bypass behaves exactly as it does now, just routed through the same merge path instead of the caller having already written the columns itself.

**`admin.transition_record_status`**, `validate` operation:
- Before flipping status, look up `admin.record_pending_changes` for `(table_name, record_id)`.
- If found: merge `proposed_changes` onto the real row via `jsonb_populate_record` (type-safe against the table's row type, avoids hand-building per-column casts):
  ```sql
  EXECUTE format(
    'UPDATE %s AS t SET (%s) = (SELECT %s FROM jsonb_populate_record(NULL::%s, $1)) WHERE t.id = $2',
    v_table_qualified, v_cols_csv, v_cols_csv, v_table_qualified
  ) USING v_pending.proposed_changes, p_record_id;
  ```
  (`v_cols_csv` = comma-joined keys of `proposed_changes`, via `jsonb_object_keys`.) Then delete the consumed `record_pending_changes` row.
- Re-fetch `v_new_row` **after** the merge — the existing `subscription_plans`-specific `pricing_change_history` insert in this function (added for the validate case) already reads `v_new_row` for the diff; it needs the merged values, not the pre-merge ones. This is an ordering fix within the existing function, no new logic needed there.
- If no pending-changes row is found (bypass path that had none, or a legacy in-flight record from before this migration — see §6), behave exactly as today.

- **New `reject` operation**, distinct from `delete`: `unauthorised → previous_status` (from the consumed `record_pending_changes` row, defaulting to `live` if no pending row exists). Discards the pending changes, does **not** touch the real row's fields — they were never modified, so there's nothing to revert. `delete` is kept unchanged for the explicit user-initiated "Delete" action from the unauthorised state (per the original lifecycle diagram in v15 §1) — that one still moves the record to `history`.

**`admin.process_authoriser_decision`**, rejection branch: call `transition_record_status(..., 'reject', ...)` instead of `'delete'`. This is the behavioral fix that makes rejection sane under defer-apply — today, rejecting an edit moves the *entire record* to `history` (because under Bug B the row already held the bad values, so "get it off the live list" was the only option); after this fix, rejecting simply discards the proposed edit and the record stays `live` with its last-approved values, which is what a maker/checker reject should do.

**The four update RPCs** (`update_subscription_plan`, `update_affiliate`, `update_payment_gateway`, `admin_upsert_cancellation_category`) — same shape of change to each:
- Compute the changed-field set as today (`v_material_change` equivalent).
- If governance is active for that table **and** something changed: skip the direct `UPDATE` entirely for the governed columns, build `proposed_changes` as a JSONB object of just the changed fields, and call `admin.submit_for_authorisation(...)` with it. Nothing about the whole edit applies until validated — simpler to reason about than splitting "material" vs. "cosmetic" fields across an immediate write and a deferred one.
- If not governed / no active authorisers: apply the `UPDATE` immediately, exactly as today (bypass path unchanged, including `subscription_plans`' existing immediate `pricing_change_history` insert, which is already correctly gated by `NOT v_governance_active`).
- `admin_upsert_cancellation_category`'s `p_id IS NULL` (create) branch is untouched — governance only applies to edits of an existing row, matching how `create_subscription_plan` already bypasses governance entirely today.

## 5. Frontend — approvers need to see what's actually changing

This is a consequence of the fix that isn't optional: today, an approver looking at an `unauthorised` record can just read its (already-applied) fields to see what it's about to become. After defer-apply, the row still shows the **old** values while pending — so without a diff view, the approver has no way to see what they're validating. This must ship together with §4, not as a follow-up.

- New RPC `admin.get_pending_changes(table_name, record_id)` → JSONB (`previous_status`, `proposed_changes`, `submitted_by`, `submitted_at`), gated the same way as other lifecycle reads (`lifecycle.authorise`, `lifecycle.configure`, or the table's own view permission).
- `packages/shared/src/lifecycleServices.js`: add `fetchPendingChanges(tableName, recordId)` wrapper.
- `packages/ui/src/RecordLifecycle.jsx`: new `PendingChangesDiff` component (field / current value / proposed value), rendered inside `RecordLifecyclePanel` whenever `record_status === 'unauthorised'` — sits directly below the banner + auto-expanded panel already shipped in §0, so the two fixes read as one coherent piece of UI rather than two unrelated patches.
- Wire into all four pilot pages' governance panels (`PlanCatalogFormPage`, `AffiliateFormPage`, `PaymentGatewayFormPage`, cancellation category edit modal), not just subscriptions.

## 6. Migration note — existing in-flight records

Any record currently sitting in `unauthorised` status (e.g. the "Basic Monthly" plan from the bug report, if still unresolved) has no `record_pending_changes` row, because its "new" values are already baked into the live columns under the old behavior — there's no prior state left to recover. Document this as a one-time transition: those specific rows should be manually validated or deleted the old way (Bug A's quick fix already makes the Validate button reachable) **before** or immediately after this migration runs, since after this migration a `validate` on a row with no pending-changes entry just flips status with no merge (harmless no-op merge, current values stand as-is) and a `reject` on one falls back to `previous_status = 'live'` by default (safe default, matches intent).
