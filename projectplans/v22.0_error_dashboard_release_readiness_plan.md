# v22.0 — Error Dashboard Fix + Release Readiness Indicator

## Status: COMPLETE

## Background

User asked for a dev-phase workflow: review auto-logged errors, fix them, mark resolved, and have a clear signal that no known errors are shipping to production. Investigation of the existing system (`modules/errors`, `SQL/v06_error_functions.sql`, `SQL/v17_admin_error_reporting_enrichment.sql`) found the infrastructure mostly already exists:

- `ModuleErrorBoundary` + global `window` error/rejection handlers → `reportClientError()` (`packages/shared/src/errorReporting.js`) → raw rows in `admin.system_error_log`.
- An `AFTER INSERT` trigger (`admin.process_error_event()`) aggregates by `error_hash` into `admin.error_aggregations` (`status`: new/acknowledged/investigating/resolved/ignored/recurring; `severity`: low/medium/high/critical) and auto-creates `[Auto]` support tickets past a threshold.
- The Error Dashboard (`modules/errors/src/pages/ErrorDashboardPage.jsx`, `ErrorDetailPage.jsx`) already lets admins filter, and resolve/ignore/reclassify individually or in bulk.
- If a resolved error recurs, status flips back to `recurring` automatically — correct regression-detection behavior, kept as-is.

Two things were missing, one of them a **confirmed live bug**, verified directly against the running database (not just tracked SQL):

### Confirmed bug — Error Dashboard resolve/ignore/reclassify is completely broken today

`admin.update_error_status` and `admin.update_error_severity` (`SQL/v06_error_functions.sql:25,84`) check permission key `'errors.edit'`. Queried `admin.admin_permissions` and `admin.role_permissions` directly:

- `'errors.edit'` **does not exist** in `admin_permissions` at all.
- The actually-seeded, actually-granted key (to `super_admin`, `system_admin`, `support_admin` — matching the nav-visible role list) is `'errors.status.manage'`.
- The Error Dashboard buttons have no client-side `PermissionGate` — they render for everyone with nav access, so every admin can click Resolve/Ignore/change severity, and every click currently fails server-side with `Permission denied: errors.edit required`.

This looks like a permission-key rename that was applied to the seed data but never propagated to the two RPC functions that enforce it. **Nobody can currently resolve an error from the dashboard**, which directly blocks the workflow being requested — fixing this is a prerequisite, not optional polish.

### Missing — no release-readiness signal

Grepped the repo for `release_gate|known_issue|block_release|production_ready` — no matches. Nothing today answers "are there open critical errors right now" as a go/no-go check. Testing Centre's defect tracking (`public.bugs`) is a separate system with no foreign key to `error_aggregations` — linking the two is real future work, but out of scope here (see Non-goals).

## Goals

- Fix the permission mismatch so resolve/ignore/reclassify actually works.
- Add a read-only **Release Readiness** indicator: open error counts by severity, with a clear blocked/clear signal, surfaced where a developer will actually see it before shipping — the Error Dashboard itself and the main Admin Dashboard.
- Make the "what counts as blocking" threshold configurable (reuse the existing `admin.get_system_setting()` pattern already used for auto-ticket thresholds), defaulting to "any open critical severity error blocks."

## Non-goals

- **Error ↔ Testing Centre defect linking.** Recommended as a fast-follow once the lean version proves useful, not bundled here — it's a bigger surface (new FK column, UI in two modules, bidirectional linking) and the lean readiness indicator already satisfies the core ask without it.
- **Changing recurrence behavior.** A resolved error flipping back to `recurring` on reoccurrence is correct and stays as-is.
- **CI/build-time enforcement.** This is an in-app dashboard signal for developers, not a CI gate that blocks deploys — no GitHub Actions changes.

## Phase 1 — Fix the permission bug ✅

File: `SQL/v151_error_dashboard_permission_fix.sql`

- `admin.update_error_status` and `admin.update_error_severity`: change the permission check from `'errors.edit'` to `'errors.status.manage'` (the key that's actually seeded and granted to `super_admin`/`system_admin`/`support_admin`).
- No seed-data change needed — `errors.status.manage` already exists and is already granted correctly; only the RPC-side check string was wrong.
- Manual verification: as a `support_admin`, resolve an error from `ErrorDetailPage.jsx` and confirm no permission error.

## Phase 2 — Release readiness RPC ✅

File: `SQL/v152_error_release_readiness.sql`

- `admin.get_error_readiness_summary()` — `STABLE SECURITY DEFINER`, gated by `errors.dashboard.view` (existing key). Returns:
  ```
  TABLE(severity TEXT, open_count INTEGER)
  ```
  grouped over `admin.error_aggregations` where `status IN ('new','acknowledged','investigating','recurring')` (excludes `resolved` and `ignored` — ignored means an admin explicitly decided it's not blocking).
- `admin.get_system_setting('errors.release_gate_severity_threshold', 'critical')` — configurable threshold (`critical` or `critical,high`), read by the frontend to decide the blocked/clear banner color, keeping the RPC itself dumb (just counts) and the policy in the existing settings mechanism.
- Add the threshold key to `admin.system_settings` seed defaults alongside the existing `errors.auto_ticket_*` keys, same file.

## Phase 3 — Frontend: readiness banner ✅

Files: `modules/errors/src/pages/ErrorDashboardPage.jsx`, `packages/shared/src/ReleaseReadinessBanner.jsx`, `packages/shared/src/dataServices.js` (add `fetchErrorReadinessSummary`), `shell/src/pages/dashboard/AdminDashboard.jsx`

- `ReleaseReadinessBanner` — small reusable component in `@nidus-admin/shared` (shared so shell Admin Dashboard can import without federation coupling): calls `fetchErrorReadinessSummary`, renders blocked/clear signal based on the configured threshold. Links to the Error Dashboard filtered by blocking severity.
- Mount it at the top of `ErrorDashboardPage.jsx` (primary location — where a dev is actually triaging).
- Mount a compact version as a card on `AdminDashboard.jsx` (visibility without requiring someone to remember to check the Error Dashboard specifically).
- `PermissionGate` added for `errors.status.manage` on dashboard/detail status actions.
- No new nav entry — reuses existing Error Dashboard page and Admin Dashboard.
