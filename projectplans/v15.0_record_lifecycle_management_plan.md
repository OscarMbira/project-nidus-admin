## 1. What this is

The diagram specifies a maker-checker (four-eyes) authorisation workflow combined with a four-state record lifecycle:

```
User creates/amends record
        │
        ├── Zero Authorisers ─────────────────────────────► LIVE (bypass)
        │
        └── ≥1 Authoriser ──► UNAUTHORISED
                                  │  Input, Delete, Amend, See, Validate, Print
                                  │ (Validate / all authorisers approve)
                                  ▼
                                LIVE
                                  │  Input, Reverse, Amend, See, Validate, Print
                                  │ (Amend/Reverse → old version snapshotted)
                                  ▼
                              HISTORY
                                  │  Restore, See, Print
                                  │ (Archive)
                                  ▼
                              ARCHIVE
                                     See, Print (final state)

Cross-cutting: "User/System Queries" can read across ALL four states,
for any registered table, at once.
```

This is **already built** for Platform and Simulator (`public` and `sim` schemas) under v639/v651–v669. This plan ports the same governance pattern into the **`admin`** schema, adapted to the Admin app's own conventions (`admin.check_admin_permission()`, `admin.log_admin_action()`, `admin.admin_users`, `admin.role_permissions`/`admin.admin_permissions`) rather than importing anything cross-repo (Admin never imports from the monorepo — SQL is duplicated/adapted, not shared, per the Admin `CLAUDE.md`).

## 2. Why the Admin adaptation differs from Platform/Simulator

| Aspect | Platform/Simulator (v639) | Admin (this plan) |
|---|---|---|
| Schema | `public` / `sim` | `admin` |
| Scope keys | `account_id` + `project_id` (multi-tenant, per-org config) | **Global only** — Admin is a single console; no per-tenant scoping. `record_lifecycle_config` keys on `table_name` alone. |
| Volume profile | Category A (risks, issues, tasks — 100k+ rows) needed physically separate `_history`/`_archive` tables | Every Admin-governed table is low volume (tens to low-thousands of rows: pricing plans, affiliate tiers, cancellation reasons, payment config). **Category B only** — a `record_status` column added directly to the existing table, no physical table split. |
| Authoriser identity | `public.users` | `admin.admin_users` |
| Permission check | `is_user_pmo_admin()` | `admin.check_admin_permission(admin_user_id, permission_key)` |
| Audit trail | `record_lifecycle_logs` only | `record_lifecycle_logs` (fine-grained state machine trail) **plus** every transition also calls the existing `admin.log_admin_action()` so it shows up in the standard Admin audit log alongside every other admin action — Admin already has a mature audit system (`modules/audit`) that this must feed into, not duplicate. |
| Prior art to reconcile | N/A | `admin.pricing_change_history` (from `v92`) already tracks price changes on `subscription_plans`. This plan **absorbs** that table's purpose into the generic `record_lifecycle_logs`/`record_authorisation_requests` trail rather than keeping two parallel change-history mechanisms for the same table (see §5). |

## 3. Scope decision: which Admin tables get the lifecycle (pilot)

Not every Admin table needs four-eyes governance — this pattern is for **records where an unreviewed change has real financial, contractual, or compliance impact**. Recommended pilot (v1), all currently ungoverned or only weakly governed:

| Table | Why it qualifies | Current state |
|---|---|---|
| `public.subscription_plans` (admin-managed catalog) | Price changes directly affect billing for all subscribers | Has ad hoc `admin.pricing_change_history` (v92) — logs changes but never blocks/requires approval. Superseded by this plan (history table kept for read compat, populated automatically from the lifecycle log; see §5). |
| `admin.affiliate_program_config` / commission-tier tables (v56/v57) | Commission rate changes affect payouts | No governance today. |
| `admin.payment_configuration` (v46/v47) | Payment gateway/fee config; misconfiguration can break checkout | No governance today. |
| `admin.cancellation_reasons` (v63/v64) | Lower stakes, but a good low-risk table to validate the full UI/UX pattern on before wider rollout | No governance today. |

**Explicitly out of scope for this plan:** `admin.refund_requests` (already has its own bespoke 5-status approval workflow from v54/v55 — do not retrofit; revisit only if the two patterns should later be unified, as a separate follow-up plan) and anything in `admin.audit_log`/`admin.admin_actions` (those are themselves the ledger, not governed records).

Everything else (feedback, testing centre, docs centre, email centre, system testers) is left ungoverned in v1. Because the config table (`admin.record_lifecycle_config`) is keyed by `table_name`, **adding a new governed table later is a seed-data change, not a schema change** — this is the same extensibility model Platform used (only `risks`/`issues`/`projects` got full list-page integration initially; the plan notes the rest as follow-up).

*(This pilot list is a recommendation for you to adjust when approving — swap/add/remove tables freely; the infrastructure in §4–§6 doesn't change either way.)*

## 4. Schema (new SQL, `admin` schema)

Mirrors `v651`/`v654` from the reference implementation, minus `account_id`/`project_id` scoping and minus the Category A physical-table split.

**`admin.record_lifecycle_config`** — per-table governance switch
`id, table_name UNIQUE, approval_enabled BOOL DEFAULT TRUE, level_approval_mode ('any'|'all') DEFAULT 'any', history_retention_days, auto_archive_enabled BOOL DEFAULT FALSE, archive_retention_years, is_active, configured_by → admin.admin_users, created_at, updated_at`

**`admin.record_authorisers`** — who can approve, per table, per level
`id, table_name, authoriser_admin_user_id → admin.admin_users, approval_level INT DEFAULT 1, role_label, is_active, created_by, created_at, updated_at`
`UNIQUE(table_name, authoriser_admin_user_id)`

**`admin.record_authorisation_requests`** — one row per authoriser per submission batch
`id, table_name, root_record_id, record_id, submission_batch_id, submitted_by, authoriser_id, approval_level, role_label, status ('waiting'|'pending'|'approved'|'rejected'|'withdrawn'), submission_notes, decision_notes, submitted_at, activated_at, decided_at`

**`admin.record_lifecycle_logs`** — fine-grained transition trail (feeds `admin.log_admin_action` too, see §5)
`id, table_name, root_record_id, record_id, from_status, to_status, operation, performed_by, reason, version_number, snapshot_data JSONB, performed_at`

**`admin.record_archive_config`** — optional per-table retention override (regulatory reasons), same shape as v639's `record_archive_config` minus `account_id`.

RLS: config/authoriser tables restricted to admins holding `lifecycle.configure`; authorisation requests visible to the requester, the assigned authoriser, or anyone holding `lifecycle.configure`; logs are insert-by-system/select-by-any-admin (read-only audit trail), same posture as `admin.audit_log`.

## 5. Category B columns on pilot tables

For each pilot table, add (idempotent `ADD COLUMN IF NOT EXISTS`, mirroring `v653`'s `ensure_lifecycle_category_b()` helper adapted to `admin`/`public` cross-schema targets):

```
record_status   TEXT NOT NULL DEFAULT 'live'
                CHECK (record_status IN ('unauthorised','live','history','archived')),
root_record_id  UUID,   -- backfilled to id for existing rows; groups all versions of one logical record
record_version  INTEGER NOT NULL DEFAULT 1,
parent_record_id UUID,  -- previous version, for Restore/version-chain UI
authorised_by   UUID REFERENCES admin.admin_users(id),
authorised_at   TIMESTAMPTZ,
archived_at     TIMESTAMPTZ,
archived_by     UUID REFERENCES admin.admin_users(id)
```

Backfill migration sets `record_status='live'`, `root_record_id=id`, `record_version=1` for every existing row — nothing currently in these tables goes through authorisation retroactively.

**`subscription_plans` reconciliation:** the existing `admin.update_subscription_plan()` RPC (v92) currently writes directly to `pricing_change_history` and applies the price change immediately. This plan changes that RPC so a price change on a governed plan goes through `admin.submit_for_authorisation()` instead of applying immediately when `approval_enabled=TRUE` for `subscription_plans` and authorisers exist — i.e. **the existing CRUD RPCs gain a lifecycle gate, they are not replaced.** `pricing_change_history` keeps being written (for the existing pricing-history UI to keep working) but only at the point the change actually goes live (on `validate`), not at submission time.

## 6. Functions (new SQL, `admin` schema, `SECURITY DEFINER`)

Direct ports of `v654`, renamed into `admin.*` and re-pointed at `admin.admin_users` / `admin.check_admin_permission()`:

- `admin.get_lifecycle_config(table_name)` → JSONB
- `admin.get_authoriser_count(table_name)` / `admin.get_approval_chain(table_name)` → JSONB
- `admin.submit_for_authorisation(table_name, record_id, root_record_id, submitted_by, notes)` → batch UUID — bypasses straight to `live` when zero authorisers or `approval_enabled=false`
- `admin.process_authoriser_decision(request_id, decision, notes)` → JSONB — same any/all level-progression and rejection-cascade logic as `process_authoriser_decision` in v654
- `admin.get_approval_progress(submission_batch_id)` → JSONB
- `admin.transition_record_status(table_name, record_id, operation, notes)` → JSONB — handles `validate`/`delete`/`archive`/`restore`; **every call also invokes `admin.log_admin_action()`** with `action = '{table}.lifecycle.{operation}'` so it appears in the standard Admin audit log module
- `admin.get_record_lifecycle_chain(table_name, root_record_id)` → JSONB — full version history for a record
- `admin.get_current_version(table_name, root_record_id)` → JSONB

No `archive_history_record` port needed (that function only exists for Category A's physical `_history`→`_archive` move; Category B archival is just a status flip via `transition_record_status`).

## 7. Permissions & seed data

New permission keys registered in `admin.admin_permissions` (pattern from `v82`):

| Key | Meaning |
|---|---|
| `lifecycle.configure` | Manage lifecycle config, authorisers, archive retention rules for any governed table |
| `lifecycle.authorise` | Act as an authoriser (appear in the Validate/Reject queue) — actual eligibility is still per-table via `record_authorisers` |
| `lifecycle.view_all` | View records across all four states regardless of table-specific view permission (the "User/System Queries" cross-state read) |

Default role grants (via `admin.role_permissions`): `super_admin` gets all three; `system_admin` gets `lifecycle.authorise` + `lifecycle.view_all`. Seed file also inserts one `record_lifecycle_config` row per pilot table (`approval_enabled=TRUE`, `level_approval_mode='any'`) — **with zero rows in `record_authorisers` initially**, meaning every pilot table starts in **zero-authoriser bypass mode** (changes apply immediately, same as today) until you explicitly assign authorisers per table. This makes the rollout non-disruptive by default.
