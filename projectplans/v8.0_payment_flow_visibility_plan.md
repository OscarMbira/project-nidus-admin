**Status:** Complete
**Created:** 2026-06-27
**Author:** Claude (for review)
**Depends on:** v7.0 Payment Configuration (Complete)

## Overview

Gives admins full visibility into the payment system across five layers:

| Layer | Feature | Where |
|---|---|---|
| **1** | Payment Flow Diagram — visual map of how payments are routed | `/subscriptions/payment-flow` |
| **2** | Transaction Monitor — live feed of all payment events and outcomes | `/subscriptions/payment-monitor` |
| **3** | Payment Journey — per-subscription payment timeline | Tab on existing Subscription Detail page |
| **4** | Payment Dashboard — aggregated metrics, charts, and KPIs | `/subscriptions/payment-dashboard` |
| **5** | Payment Reports — pre-built downloadable payment-specific reports | `/subscriptions/payment-reports` |

Layers 1 and 3 require no new backend beyond what v7.0 already built. Layer 2 requires one new table (`admin.payment_events`). Layers 4 and 5 build on that same table with additional aggregation RPC functions — no further tables needed.

### Layer 1 — Payment Flow Diagram (`/subscriptions/payment-flow`)

**Purpose:** A visual, auto-generated map of the entire payment routing architecture. Reads live from `admin.payment_method_routing` and `admin.payment_gateways` — no manual diagramming, always reflects current configuration.

**Layout:** Full-width canvas split into three swim lanes:

```

│   CUSTOMER       │   PAYMENT METHODS    │   GATEWAYS       │
│   REGIONS        │                      │                  │
├─────────────────┼──────────────────────┼──────────────────┤
│  🇿🇼 Zimbabwe   │──► EcoCash           │──► [PayNow]      │
│                 │──► OneMoney          │──► [PayNow]      │
│                 │──► Telecash          │──► [PayNow]      │
│                 │──► ZimSwitch         │──► [PayNow]      │
│                 │──► ZIPIT Transfer    │──► [PayNow]      │
│                 │──► Card              │──► [Flutterwave] │
│                 │                      │    fallback ──►  │
│                 │                      │    [Paddle]      │
├─────────────────┼──────────────────────┼──────────────────┤
│  🌍 Africa      │──► M-Pesa            │──► [Flutterwave] │
│  (non-ZW)       │──► MTN MoMo          │──► [Flutterwave] │
│                 │──► Airtel Money      │──► [Flutterwave] │
│                 │──► Vodafone Cash     │──► [Flutterwave] │
│                 │──► Card              │──► [Flutterwave] │
├─────────────────┼──────────────────────┼──────────────────┤
│  🌐 Global      │──► Card              │──► [Paddle]      │
│  (US/EU/ME/Asia)│──► PayPal            │──► [Paddle]      │
│                 │──► Apple Pay         │──► [Paddle]      │
│                 │──► Google Pay        │──► [Paddle]      │
└─────────────────┴──────────────────────┴──────────────────┘
```

**Node colours:**
- Green — active and enabled
- Grey — disabled / inactive
- Orange dashed line — fallback route
- Red — gateway is inactive (warning state)

**Interactivity:**
- Click a **gateway node** → drawer slides in showing gateway config summary (name, environment, status, last updated) with a link to the gateway detail page
- Click a **method node** → drawer shows that routing rule's full config (primary/fallback gateway, countries, fees)
- Click a **region node** → highlights all routes for that region, dims others
- **Country preview input** at the top: admin types a country code (e.g. `KE`) and the diagram highlights only the routes that customer would see — same logic as the routing preview in Method Routing page, but visualised

**Toolbar:**
- Toggle: Show inactive routes / Hide inactive routes
- Toggle: Show fallback paths / Hide fallback paths
- Export as PNG (for documentation / handover)

**Data source:** Reads directly from `admin.payment_method_routing` joined to `admin.payment_gateways` and `admin.payment_methods`. No new backend needed — uses existing `paymentConfigServices.js` functions.

**No new RPC functions required for this layer.**

### Layer 2 — Transaction Monitor (`/subscriptions/payment-monitor`)

**Purpose:** A live, filterable feed of all payment attempts across all gateways. Answers "what is happening with payments right now?" and "why did this payment fail?"

**Page layout:** Stats bar + filters + live table.

**Stats bar (auto-refreshes every 30 seconds):**

| Stat | Description |
|---|---|
| Total Today | Count of all payment attempts today |
| Success Rate | % of today's attempts that succeeded |
| Active Retries | Count of payments currently in retry queue |
| Gateway Alerts | Count of gateways with >10% failure rate in last hour |

**Filter bar:**
- Date range picker (default: last 24 hours)
- Gateway selector (All / PayNow / Flutterwave / Paddle)
- Status filter (All / Success / Failed / Pending / Retrying / Refunded)
- Country selector
- Search by customer email or transaction ID

**Table columns:**

| Column | Notes |
|---|---|
| Time | Timestamp of event |
| Customer | Email — links to User Detail page |
| Country | ISO flag + code |
| Method | e.g. EcoCash, M-Pesa, Card |
| Gateway | PayNow / Flutterwave / Paddle |
| Amount | USD amount |
| Status | Badge: Success / Failed / Pending / Retrying |
| Retry # | Which attempt (blank if first and succeeded) |
| Duration | ms from initiation to outcome |
| Actions | View Journey button |

**Row click / View Journey button** → opens the Payment Journey drawer (see Layer 3) for that transaction's subscription.

**Realtime:** Supabase Realtime subscription on `admin.payment_events` — new rows appear at the top without refresh.

**Export:** Export filtered results to CSV.

### Layer 3 — Payment Journey (Tab on Subscription Detail)

**Purpose:** Per-subscription full payment history displayed as a vertical timeline. Answers "what happened with this specific customer's payments?"

**Location:** New **Payments** tab added to the existing `SubscriptionDetailPage.jsx` alongside the existing tabs (Details, Features, etc.).

**Timeline entry format:**

```
● 2026-06-27 09:00:01   Payment Initiated
  Method: EcoCash  ·  Gateway: PayNow  ·  Amount: $29.00

✗ 2026-06-27 09:00:03   Payment Failed
  Reason: Insufficient funds  ·  Duration: 2,341ms
  → Retry scheduled in 1 hour

● 2026-06-27 10:00:01   Retry Attempt 1
  Method: EcoCash  ·  Gateway: PayNow  ·  Amount: $29.00

✓ 2026-06-27 10:00:04   Payment Successful
  Transaction ID: PAY-ZW-2026-00891  ·  Duration: 3,102ms

📄 2026-06-27 10:00:05   Invoice Issued
  Invoice #INV-2026-00042  ·  Link to invoice
```

**Event types and icons:**
- ● Blue — initiated
- ✓ Green — success
- ✗ Red — failed
- 🔄 Orange — retry scheduled / retry attempt
- 📄 Grey — invoice issued
- 💰 Purple — refund processed

**No new backend needed** — reads from `admin.payment_events` filtered by `subscription_id`. The data is populated by the same event log that powers the Transaction Monitor.

## SQL Plan

### `v48_payment_events.sql`

Only Layer 2 and 3 need new DB objects. Layer 1 is purely frontend.

#### New Table: `admin.payment_events`

```sql
admin.payment_events
  id UUID PK DEFAULT gen_random_uuid(),
  subscription_id UUID,              -- FK to platform or sim subscription (nullable)
  user_id UUID,                      -- platform user
  gateway_id UUID REFERENCES admin.payment_gateways(id),
  payment_method_id UUID REFERENCES admin.payment_methods(id),
  event_type TEXT NOT NULL CHECK (event_type IN (
      'initiated', 'success', 'failed', 'retry_scheduled',
      'retry_attempt', 'refunded', 'cancelled', 'invoice_issued'
  )),
  target_system TEXT CHECK (target_system IN ('platform', 'simulator')),
  amount NUMERIC(12,2),
  currency VARCHAR(3) DEFAULT 'USD',
  country_code CHAR(2),
  attempt_number INTEGER DEFAULT 1,
  transaction_id TEXT,               -- gateway-assigned transaction reference
  failure_code TEXT,                 -- gateway failure code if event_type = 'failed'
  failure_message TEXT,              -- human-readable failure reason
  duration_ms INTEGER,               -- ms from initiation to this event
  gateway_response JSONB,            -- raw gateway response (sanitised — no PII)
  invoice_id UUID REFERENCES admin.invoices(id),
  retry_rule_id UUID REFERENCES admin.payment_retry_rules(id),
  next_retry_at TIMESTAMPTZ,         -- populated when event_type = 'retry_scheduled'
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
```

**Indexes:**
```sql
idx_payment_events_subscription_id  (subscription_id)
idx_payment_events_user_id          (user_id)
idx_payment_events_gateway_id       (gateway_id)
idx_payment_events_event_type       (event_type)
idx_payment_events_created_at       (created_at DESC)
idx_payment_events_country_code     (country_code)
```

No `updated_at` — this is an immutable event log. Rows are never updated, only inserted.

#### RPC Functions

| Function | Permission | Purpose |
|---|---|---|
| `admin.list_payment_events(filters)` | billing.payment_config.view | Transaction Monitor feed with filters |
| `admin.get_payment_journey(subscription_id, target_system)` | billing.payment_config.view | Payment Journey timeline per subscription |
| `admin.get_payment_monitor_stats(from_ts, to_ts)` | billing.payment_config.view | Stats bar totals (success rate, retry count, alerts) |
| `admin.log_payment_event(...)` | service_role only | Called by payment processing logic to write events |

`admin.list_payment_events` accepts:
- `p_from` / `p_to` TIMESTAMPTZ
- `p_gateway_id` UUID (nullable)
- `p_status` TEXT (nullable)
- `p_country_code` CHAR(2) (nullable)
- `p_search` TEXT (email or transaction_id, nullable)
- `p_limit` INTEGER DEFAULT 100
- `p_offset` INTEGER DEFAULT 0

`admin.log_payment_event` has `SECURITY DEFINER` and is restricted to `service_role` — it is never called from the browser. Only the payment processing backend (COB batch / subscription renewal) writes to this table.

All read functions grant to `authenticated, service_role`.

## Frontend Plan

### New Pages / Components

| File | Route / Location | Purpose |
|---|---|---|
| `PaymentFlowPage.jsx` | `/subscriptions/payment-flow` | Routing architecture diagram |
| `PaymentMonitorPage.jsx` | `/subscriptions/payment-monitor` | Live transaction feed + stats |
| `PaymentJourneyTab.jsx` | Tab in `SubscriptionDetailPage.jsx` | Per-subscription payment timeline |
| `PaymentDashboardPage.jsx` | `/subscriptions/payment-dashboard` | KPIs, charts, geo breakdown, recent failures |
| `PaymentReportsPage.jsx` | `/subscriptions/payment-reports` | Report catalogue + generate + download |

### Diagram Implementation (Layer 1)

**Approach:** React Flow (`@xyflow/react`) — a lightweight, well-maintained React graph library. Nodes and edges are generated programmatically from the routing config fetch, not hardcoded.

Node types:
- `RegionNode` — Zimbabwe / Africa / Global — left column
- `MethodNode` — EcoCash, M-Pesa, Card etc — middle column
- `GatewayNode` — PayNow, Flutterwave, Paddle — right column

Edge types:
- `PrimaryEdge` — solid line, green when active
- `FallbackEdge` — dashed line, orange
- `InactiveEdge` — solid line, grey

Clicking a node opens an `AdminCard` drawer on the right with that entity's details.

Country preview: a `<select>` at the top of the page. On change, edges not matching that country are dimmed to 20% opacity.

### Transaction Monitor (Layer 2)

- Supabase Realtime channel subscribed to `admin.payment_events` INSERT events
- New events prepended to the top of the table with a fade-in animation
- Stats bar re-fetches `admin.get_payment_monitor_stats` every 30 seconds via `setInterval`
- Status badges reuse existing `AdminBadge` component with new variants: `success`, `failed`, `retrying`, `pending`

### Payment Journey (Layer 3)

- Vertical timeline built with CSS — no new library needed
- Each event type maps to an icon + colour (defined in a `EVENT_TYPE_CONFIG` map)
- Loaded as a new tab inside the existing `SubscriptionDetailPage.jsx` — no new route
- Reads from `admin.get_payment_journey(subscriptionId, targetSystem)`

### Dashboard Implementation (Layer 4)

**Charting library:** Recharts — already likely available, lightweight, composable React charts.

- KPI cards reuse the existing `AdminCard` component with a trend indicator (arrow + % change vs prior period)
- Revenue chart: `<BarChart>` with one `<Bar>` per gateway, stacked mode
- Method breakdown: `<PieChart>` with `<Cell>` per method type — click segment filters Revenue chart
- Gateway Performance: `AdminTable` with conditional row colouring (red row if success rate < 80%)
- Geographic Breakdown: `AdminTable` sorted by revenue, country flag via emoji or ISO lookup
- Recent Failed Payments: `AdminTable` with inline **View Journey** button

All sections share the date range state at the page level. Changing the date range re-fetches all sections in parallel.

### Reports Implementation (Layer 5)

**Page layout:** Grid of `AdminCard` report cards — one per report type.

Each card shows:
- Report name + description
- Last generated: `"Never"` or relative time (e.g. `"3 minutes ago"`)
- A **Generate** button with a date range picker that opens inline

On Generate:
1. RPC called → returns rows
2. Results rendered in a preview table below the card (paginated, max 10 rows shown)
3. **Export CSV** and **Export PDF** buttons appear
4. Last-generated timestamp updates

PDF export: uses `jsPDF` + `jspdf-autotable` — generates a cover page (report name, date range, generated by) + the data table.

5-minute result cache: stored in component state — re-clicking Generate within the window skips the RPC call.

### Shared Services

Add to `packages/shared/src/paymentConfigServices.js`:
- `fetchPaymentEvents(filters)`
- `fetchPaymentJourney(subscriptionId, targetSystem)`
- `fetchPaymentMonitorStats(from, to)`
- `fetchPaymentDashboardKpis(from, to)`
- `fetchPaymentRevenueChart(from, to, granularity)`
- `fetchPaymentMethodBreakdown(from, to)`
- `fetchGatewayPerformance(from, to)`
- `fetchPaymentGeographicBreakdown(from, to)`
- `fetchRecentFailedPayments(limit)`
- `generatePaymentReport(reportType, params)` — single wrapper that calls the correct RPC per report type
