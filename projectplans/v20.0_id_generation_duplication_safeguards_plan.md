# v20.0 — ID Generation: Duplication Safeguards & Capacity Guardrails

## Status: COMPLETE

## Background / audit findings

Reviewed the existing ID generation system (`SQL/v19_id_generation.sql`, `SQL/v30_id_generation_segment_type.sql`, `modules/system/src/pages/*IdGeneration*`, `packages/shared/src/useDisplayId.js`).

**What already prevents duplication (no change needed):**
- `admin.generated_ids` has a `UNIQUE (target_table, record_id)` index and a `UNIQUE (target_table, display_id)` index — the database, not application code, is the source of truth for uniqueness.
- `admin.generate_display_id()` inserts inside a `BEGIN/EXCEPTION WHEN unique_violation` block: a collision on `display_id` (two different records rolling the same code) triggers a retry with a new random code; a collision on `record_id` (two concurrent callers generating for the *same* record) returns the winner's existing row instead of erroring. This correctly handles concurrent calls from multiple browser tabs/requests.
- `admin.generated_ids` RLS grants `SELECT` only to `authenticated`; all writes happen via `SECURITY DEFINER` RPCs, so there's no client-side path that can insert an ID directly.
- Active-rule uniqueness (`target_table`, `table_abbreviation`) is enforced by partial unique indexes (`WHERE is_active = TRUE`), not just app-level `EXISTS` checks, so a race between two admins creating rules for the same table fails at the DB, not silently.

**Real gaps — where duplication risk or duplication-adjacent failure can still occur:**

1. **No keyspace-vs-volume guardrail.** A rule can be saved with e.g. 1 letter + 0 digits (26 possible codes) for a table expected to grow unbounded. Nothing warns the admin at configure time. As the table fills, `generate_display_id` retries collide more (birthday paradox) and eventually exhausts its **hard-coded 5 attempts**, raising a raw Postgres exception to the UI.
2. **No visibility into collision pressure.** There's no metric/log showing how many retry attempts generation is taking per rule, so a rule silently approaching exhaustion gives no advance warning before it starts failing record creation.
3. **Reactivating/reusing an abbreviation across time is legal by design** (only *active* rules are constrained), so `ACC-1234` generated under an old, now-inactive rule for table X and `ACC-1234` generated later under a new rule for table Y are both valid rows (different `target_table`, so no DB conflict) but are visually indistinguishable in exports/support tickets that don't carry the table name. Low severity, but worth a UI disambiguation.
4. **No regression test proves the concurrency guarantee.** The unique-constraint-plus-retry design is correct today, but nothing in `e2e/` or SQL exercises concurrent calls to catch a future refactor that breaks it (e.g., someone "optimizing" by removing the exception handler).
5. **Client-side preview math (`idGenerationPreview.js`) and server math (`_id_gen_build_code`) both compute a sample code but neither computes total keyspace size** — needed for gap 1.

## Goals

- Add a keyspace-capacity check so admins can't unknowingly configure a format too small for the table's expected growth, and get an explicit warning as usage approaches saturation.
- Make exhaustion fail loudly and actionably (clear error + admin alert) instead of a raw exception, and raise the retry ceiling with backoff so transient collisions don't surface as user-facing errors.
- Add lightweight observability: track attempts-per-generation and surface a "capacity used" indicator per rule on the ID Generation Rules page.
- Add a regression test that proves uniqueness holds under concurrent generation for the same record and for different records.
- Document the guarantees and operational guidance in `modules/system/docs/`.

## Non-goals

- No change to the random-code algorithm itself (still DB-random, not sequential) — out of scope, and the current approach is sound.
- No change to how `target_table`/`table_abbreviation` uniqueness is enforced — already correct.

## Phase 1 — SQL: capacity math, higher retry ceiling, generation stats

File: `SQL/v138_id_generation_capacity_safeguards.sql`

1. `admin._id_gen_keyspace_size(num_letters, num_digits, letter_case, excluded_chars, segment_type) RETURNS BIGINT` — pure function computing the true alphabet size per position (26 or 52 for mixed-case letters, 10 for digits, minus excluded characters) and returning the total permutation count. Mirror this exact formula client-side in `idGenerationPreview.js` (`computeKeyspaceSize`) so the form preview and the DB agree.
2. `admin.generate_display_id`: raise `v_attempt` ceiling from 5 to a config-driven value (start at 20) and add exponential jitter is unnecessary at DB level (random() is already independent per call) — just raise the ceiling. On final exhaustion, raise a distinguishable error code/message (e.g. `SQLSTATE 'P0001'` with message prefixed `ID_KEYSPACE_EXHAUSTED:`) so the frontend can show a specific "this table's ID format has run out of unique codes — contact a system admin to widen it" message instead of a generic failure toast.
3. Add `admin.generated_ids_stats` (or a computed view `admin.v_id_generation_rule_usage`) exposing, per active rule: `keyspace_size`, `generated_count` (from `generated_ids` join), `usage_pct`. Compute on read (STABLE SQL function), not a maintained counter table — avoids a new write path.
4. `admin.create_id_generation_rule` / `admin.update_id_generation_rule`: no hard block (admins may legitimately want a short-lived small-volume table), but return the computed `keyspace_size` in the RPC result (or a companion `admin.preview_id_generation_capacity(...)` RPC) so the UI can warn inline — "this format allows ~676 unique IDs; table X already has 1,240 rows" — before save. Block only the pathological case: keyspace smaller than the **current row count** of `target_table` at save time (that configuration is guaranteed to exhaust immediately).
5. Backfill: none needed — additive only.

## Phase 3 — Regression test for concurrency safety

- Add an SQL-level test (or a small Node script under `e2e/` using two concurrent Supabase RPC calls via `Promise.all`) that:
  - Calls `generate_display_id(table, sameRecordId)` twice concurrently → asserts both calls return the identical `display_id` and only one row exists in `generated_ids`.
  - Calls `generate_display_id(table, recordA)` and `generate_display_id(table, recordB)` concurrently many times (e.g. 50 pairs) against a rule with a small keyspace to force collisions → asserts all resulting `display_id`s are distinct and no error surfaces (validating the retry path actually engages).
  - Configures a rule with keyspace smaller than a batch of records requested → asserts the `ID_KEYSPACE_EXHAUSTED:` error surfaces cleanly rather than a duplicate or silent failure.
- Location: `e2e/tests/admin/id-generation-concurrency.spec.js` (Playwright can drive this via direct RPC calls through the app's Supabase client if a UI harness isn't natural — a Node/vitest integration test hitting the RPCs directly is acceptable here since this is a data-layer guarantee, not a UI flow; note this deviation and rationale in the module doc).

## Phase 5 (follow-up) — Proactive capacity alerts

The Usage column (Phase 2) only surfaces saturation risk to an admin who opens the ID Rules page. Added a pg_cron-driven check that broadcasts an in-app notification (via the existing `admin.notifications` system) for any active rule at ≥70% keyspace usage, so admins don't have to remember to look.

File: `SQL/v140_id_generation_capacity_alerts.sql`

- `admin.check_id_generation_capacity_alerts()` — scans `admin.v_id_generation_rule_usage` for rows ≥70% usage, severity `warning` (70–99%) or `critical` (≥100%). Dedupes per `rule_id` + severity tier via `metadata` on existing unexpired notifications, so it won't re-notify every 6 hours at the same tier but will re-alert on escalation to `critical`.
- Permission gate mirrors the existing cron-safe pattern in `admin.auto_archive_expired_history` (`SQL/v99_record_lifecycle_auto_archive_cron.sql`) — callable with no session (pg_cron) or by an admin holding `system.notifications.edit`.
- `admin.create_notification` has no service-role bypass, so cron-generated alerts are attributed to the longest-active `super_admin` account (resolved at call time).
- pg_cron job `admin_id_generation_capacity_check` runs every 6 hours, guarded by the same idempotent `pg_extension` check as v99's job.
- No frontend changes — the existing `NotificationBell` (polls every 60s) renders these broadcasts generically; `action_url` deep-links to `/system/id-generation-rules`.
- Known tradeoff (unchanged from the rest of the notifications system): broadcasts aren't role-scoped, so any admin with `system.notifications.view` sees the alert even if they lack `system.id_generation.edit` to act on it.
