## Context

The entire Nidus ecosystem has 3 systems with distinct roles — but zero automated tests. The sole tester currently tests every feature manually across all systems. This plan automates testing with Playwright browser automation across all 3 systems, an in-app dashboard for triggering/viewing results, and a test data factory that auto-generates realistic form data.

### Systems & Roles to Test

| System | App URL | Roles | Pages |
|---|---|---|---|
| **Admin Panel** | `localhost:5175` | super_admin, system_admin, support_admin, content_admin | 80+ pages, 13 modules |
| **Platform** | `localhost:5173` (or configured port) | pmo_admin, org_admin, project_manager, programme_manager, portfolio_manager, team_lead, team_member, executive, stakeholder, viewer | 120 pages |
| **Simulator** | `localhost:5174` (or configured port) | portfolio role, programme role, coordinator role, PMO role (via role-selection) | 120 pages |

**Current test infrastructure:** Playwright 1.61 + Vitest 3.0.5. E2E suite at `e2e/` with 17 role projects, Supabase reporter, auto-fix engine, test dashboard UI.

### Why Playwright
- Runs outside the browser — tests the real app including module federation lazy loading and Supabase auth
- Multiple browser contexts with independent auth state — test 4 roles without conflicts
- `storageState` feature — authenticate once per role in global-setup, reuse across all tests
- Built-in `codegen` tool — the tester can bootstrap new tests by clicking through the UI
- Trace/video/screenshot recording on failure

### Auto-Fix Engine: Error Categories & Strategies

| Error Category | Detection Pattern | Fix Strategy | Confidence | Auto-Apply |
|---|---|---|---|---|
| **missing_data** | `"no rows returned"`, `"not found"`, `"null"` after fetch | Re-seed required data via RPC or factory insert | HIGH | Yes |
| **permission_denied** | `"Permission denied"`, `"403"`, `"not authorized"` | Check `role_permissions` table, insert missing permission mapping | HIGH | Yes |
| **stale_state** | `"already exists"`, `"duplicate key"`, `"conflict"` | Delete stale test data matching `[TEST]` pattern, retry | HIGH | Yes |
| **validation_error** | `"required"`, `"invalid"`, `"must be"`, `"cannot be empty"` | Adjust factory data to meet validation rules, retry with corrected data | MEDIUM | Yes |
| **element_not_found** | `"waiting for selector"`, `"locator resolved to 0 elements"` | Check if route/page changed, try alternative selectors, flag if unresolvable | LOW | No (flag) |
| **db_constraint** | `"violates check constraint"`, `"violates foreign key"`, `"violates unique"` | Analyze constraint, adjust test data or clean conflicting records | MEDIUM | Yes |
| **timeout** | `"timeout"`, `"exceeded"`, `"navigation timeout"` | Increase timeout, check if server is responsive, retry once | HIGH | Yes |
| **session_expired** | `"session"`, `"401"`, `"login"` redirect | Re-authenticate the role, refresh storageState, retry | HIGH | Yes |
| **unknown** | No pattern matched | Log for manual review, suggest possible fixes based on error text | LOW | No (flag) |

### Auto-Fix Execution Flow

```
Test fails
  ↓
1. Error Classification
   → Match error_message against test_fix_patterns (regex)
   → Determine error_category and fix_strategy
   → Assign confidence level
  ↓
2. Fix Decision
   → HIGH confidence + auto_apply=true → apply fix automatically
   → MEDIUM confidence → apply fix, flag for review
   → LOW confidence → skip fix, flag as manual_required
  ↓
3. Apply Fix (if applicable)
   → Execute fix_strategy:
     • seed_missing_record → call seed RPC or insert via api-client
     • grant_permission → INSERT INTO role_permissions
     • clear_stale_data → DELETE WHERE record matches [TEST] tag
     • adjust_factory_data → regenerate with corrected constraints
     • refresh_auth → re-run login, save new storageState
     • increase_timeout → retry with 2x timeout
   → Record fix attempt in test_auto_fixes
  ↓
4. Retry Test
   → Re-run the specific failed test case
   → Record retry result
   → Update fix_status: resolved (if passed) or failed (if still fails)
  ↓
5. Report
   → Dashboard shows: auto-fixed (green), fix-failed (orange), manual-required (red)
   → Fix pattern success/failure counts updated for learning
```

## Coverage Tracking

Three levels:

1. **Route coverage** — % of sidebar routes with at least one passing test per role
2. **Operation coverage** — % of 150+ mutations and 70+ fetches exercised by tests
3. **Role × Module matrix** — pass rate grid with color coding (>95% green, >80% yellow, <80% red)

Computed by `get_test_coverage_summary()` RPC, displayed on TestDashboardPage.
