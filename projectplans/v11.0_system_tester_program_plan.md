# System Tester Program — Full Implementation Plan

**Version:** 11.2
**Created:** 2026-07-01
**Updated:** 2026-07-01
**Status:** Complete
**Scope:** End-to-end System Tester program — voluntary onboarding, configurable moratorium access (default 10 months), project role assignment, and full project-run-without-subscription capability for both Platform and Simulator.

---

## Context

The Nidus ecosystem has two live user-facing systems:

| System | Description | Roles |
|---|---|---|
| **Platform** | Project management system (projects, tasks, resources, QMS, risks, etc.) | org_admin, pmo_admin, project_manager, programme_manager, portfolio_manager, team_lead, team_member, executive, stakeholder, viewer |
| **Simulator** | PMO learning simulation (turns, scenarios, certificates) | portfolio, programme, coordinator, PMO (selected at role-selection page) |

Before a general commercial launch, the team needs **real human testers** going through the full experience. These testers:

- Register voluntarily (not employed testers — real users previewing the product)
- Get **free access for the configured moratorium period** (default: 10 months, adjustable via system settings) to one or both systems
- Are assigned to real projects and given real organizational roles in Platform
- Can run a complete project lifecycle with a team — without any member needing a subscription
- After 10 months, the moratorium ends and they are prompted to convert to paid plans

This plan covers: the application & approval flow, tester subscription provisioning, project & role assignment, sandbox team runs, admin module, SQL migrations, and best practices.

## Best Practices (Read Before Implementing)

### 1. Testers Are Real Users, Not Admins
Testers sign up and log in through the **Platform and Simulator apps** — not the Admin console. The admin console is only used by admins to approve, grant access, and assign roles.

### 2. Tester Subscriptions Are Not Free Plans
A `free` plan has limited features (1 project, basic access). Testers need **full professional-tier feature access** to test everything meaningfully. Use a distinct `tester` plan type that unlocks all features with `amount_paid = 0`.

### 3. Subscription Gate Must Honour Tester Status
Every place in Platform/Simulator that checks subscription tier must also check `is_tester`. This is the most critical integration point. A `is_tester` boolean column on subscriptions is the cleanest gate check.

### 4. Moratorium Is Time-Boxed and Centrally Configurable
The moratorium duration is driven by the `testers.default_moratorium_months` system setting (stored in `admin.system_settings`, default `10`). It can be changed by a super_admin or system_admin at any time without code changes. Individual grants can override the setting. The `expires_at` on the tester subscription controls expiry automatically — no extra logic needed.

### 4b. Tester Count Is Capped and Centrally Configurable
A `testers.max_active_testers` system setting (default `100`) prevents unbounded tester provisioning. The cap is enforced server-side in `admin.grant_tester_access()` before inserting a new tester record — if `COUNT(active testers) >= max`, the RPC raises an exception. `admin.provision_sandbox_members()` respects the same cap (provisions up to the remaining capacity, errors if already at limit). The UI shows a capacity indicator on Active Testers and Applications pages. Admins with `system.settings.edit` can raise the cap at any time without code changes.

### 5. Project Runs Require a Tester Organisation
To run a full project without subscriptions, create a dedicated **"Tester Organisation"** or flag an existing org as a tester sandbox. All members of that org inherit tester access. This avoids needing to grant individual tester subscriptions to every team member in a test run.

### 6. Role Rotation Is a Feature
Let testers request role changes (e.g. test as `team_member` week 1, `project_manager` week 2). The admin assigns new roles — the system does not need automation for this, but the UI must make it easy.

### 7. Data Cleanup Is Built In
Tester data should be flaggable: `is_tester_data = true`. This allows bulk archiving or deletion after the moratorium without touching real production data.

### 8. Conversion Is the End Goal
After the moratorium expires, testers who found value should convert to paid subscribers. Build the expiry notification flow (90-day, 30-day, 7-day, expiry-day emails) and a conversion CTA inside the app. Track conversion rate as a KPI.

### 9. Feedback Is a First-Class Tester Feature
Testers should be able to submit bug reports and feature feedback directly from the Platform/Simulator UI. The admin module (already partially built via v67–v70 feedback/bug management) should show tester submissions flagged separately.

### 10. Staging vs Production
For manual testers who are not internal staff, prefer running this program on a **staging environment** that mirrors production data schema but uses anonymised seed data. If running on production, ensure tester orgs/projects are clearly labelled to avoid confusion with real customer data.

## Admin RPCs (SECURITY DEFINER)

All RPCs live in `admin` schema and check `admin.check_admin_permission()`.

### `admin.approve_tester_application(p_application_id, p_moratorium_months DEFAULT NULL, p_grant_note, p_systems)`
- `p_moratorium_months`: if NULL, reads `testers.default_moratorium_months` from `admin.system_settings`
- Validates application is pending
- Updates status = 'approved'
- If user_id already exists: immediately calls `admin.grant_tester_access()`
- Logs action

### `admin.reject_tester_application(p_application_id, p_rejection_reason)`
- Updates status = 'rejected'
- Logs action

### `admin.grant_tester_access(p_user_id, p_systems, p_moratorium_months DEFAULT NULL, p_grant_note, p_application_id)`
- `p_moratorium_months`: if NULL, reads `testers.default_moratorium_months` from `admin.system_settings`; stored on the created record for auditability
- **Capacity check (first step):** reads `testers.max_active_testers`; counts `system_testers` rows with `status = 'active'`; raises `EXCEPTION 'Tester limit reached (max: N). Revoke inactive testers or increase testers.max_active_testers in System Settings.'` if at or over limit
- Creates `public.system_testers` row with the resolved moratorium_months and computed moratorium_end
- For each system in p_systems: creates a tester subscription with `expires_at = NOW() + (resolved_months || ' months')::INTERVAL`
- Returns tester_id
- Permission required: `testers.grant`

### `admin.revoke_tester_access(p_tester_id, p_reason)`
- Sets `system_testers.status = 'revoked'`
- Sets tester subscriptions `subscription_status = 'cancelled'`
- Permission required: `testers.revoke`

### `admin.extend_tester_moratorium(p_tester_id, p_additional_months)`
- Extends `moratorium_end` by N months
- Extends tester subscription `expires_at` by N months
- Permission required: `testers.manage`

### `admin.assign_tester_to_project(p_tester_id, p_account_id, p_project_id, p_org_role, p_project_role)`
- Inserts into `public.tester_project_assignments`
- Platform-side: calls existing org/project member RPCs to add the user to the org and project
- Permission required: `testers.assign`

### `admin.create_tester_sandbox(p_account_id, p_sandbox_name, p_moratorium_months DEFAULT NULL)`
- `p_moratorium_months`: if NULL, reads `testers.default_moratorium_months` from `admin.system_settings`
- Inserts into `public.tester_org_sandboxes` with the resolved moratorium_months and computed moratorium_end
- Permission required: `testers.sandbox`

### `admin.provision_sandbox_members(p_sandbox_id)`
- Fetches all members of the sandbox account who don't yet have tester subscriptions
- Checks `testers.max_active_testers` — if adding all unprovisioned members would exceed the cap, raises an exception with the count that CAN be provisioned vs the total requested (e.g. "5 of 12 members can be provisioned — tester limit would be exceeded")
- Calls `admin.grant_tester_access()` for each member up to remaining capacity
- Returns count of newly provisioned members
- Permission required: `testers.sandbox`

## System Settings

Both tester settings live in `admin.system_settings` under category `testers`. Any admin with `system.settings.edit` can change either value via System Settings without code changes.

### `testers.default_moratorium_months`

| Field | Value |
|---|---|
| `setting_key` | `testers.default_moratorium_months` |
| `setting_value` | `'10'` (seeded default) |
| `setting_type` | `integer` |
| `category` | `testers` |
| `description` | `Default moratorium period (months) granted to new system testers. Individual grants and sandboxes can override this value.` |

```sql
-- Inside grant_tester_access(), approve_tester_application(), create_tester_sandbox():
v_moratorium_months := COALESCE(
    p_moratorium_months,
    (SELECT setting_value::INTEGER
     FROM admin.system_settings
     WHERE setting_key = 'testers.default_moratorium_months')
);

IF v_moratorium_months IS NULL OR v_moratorium_months < 1 THEN
    RAISE EXCEPTION 'testers.default_moratorium_months system setting is missing or invalid';
END IF;
```

The resolved value is stored on `system_testers.moratorium_months` so each record is self-contained and auditable even if the global setting changes later. Changing the setting does **not** retroactively alter existing records.

---

### `testers.max_active_testers`

| Field | Value |
|---|---|
| `setting_key` | `testers.max_active_testers` |
| `setting_value` | `'100'` (seeded default) |
| `setting_type` | `integer` |
| `category` | `testers` |
| `description` | `Maximum number of concurrently active system testers. Enforced at grant time. Raise this value to allow more testers; lowering it does not revoke existing active testers.` |

```sql
-- Inside grant_tester_access() — checked BEFORE inserting:
v_max := (
    SELECT setting_value::INTEGER
    FROM admin.system_settings
    WHERE setting_key = 'testers.max_active_testers'
);
v_active_count := (
    SELECT COUNT(*) FROM public.system_testers WHERE status = 'active'
);
IF v_active_count >= v_max THEN
    RAISE EXCEPTION
        'Tester limit reached (% active / % max). Revoke inactive testers or increase testers.max_active_testers in System Settings.',
        v_active_count, v_max;
END IF;
```

**Lowering the cap** does not auto-revoke existing active testers — it only blocks new grants until the active count drops below the new limit. This avoids surprise disruption to testers already in the program.

**UI enforcement:**
- Applications page: "Approve" button disabled with tooltip when at limit.
- Active Testers page: capacity progress bar (`active / max`) — green <80%, yellow 80–99%, red 100%.
- Grant Direct Access page: same capacity bar; submit button disabled at limit.
- Sandbox provision: error returned with remaining capacity count if provisioning would exceed the cap.

**Where to change it:**
```
Admin → System → Settings → category: testers → testers.max_active_testers
```
