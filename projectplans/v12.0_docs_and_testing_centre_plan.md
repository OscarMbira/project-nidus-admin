getModules()                           // SELECT DISTINCT module FROM admin.documentation_guides WHERE is_active

### Independent Deployment

**How a doc update goes live without a code redeploy:**

```
Author edits modules/users/docs/User_Management_Guide.md
  → git push
  → GitHub Actions workflow for users module detects docs/ change
  → CI sync step runs:
      curl PUT $SUPABASE_URL/storage/v1/object/documentation/admin/users/User_Management_Guide.md
  → Supabase Storage updated
  → Live admin app fetches from Storage on next page load
  → Zero redeployment
```

**CI/CD sync step** (add to each module's existing Vite build workflow):

```yaml
- name: Sync module docs to Supabase Storage
  if: github.event_name == 'push' && github.ref == 'refs/heads/main'
  run: |
    MODULE_FOLDER="${{ matrix.module }}"
    DOCS_DIR="modules/$MODULE_FOLDER/docs"
    if [ -d "$DOCS_DIR" ]; then
      for file in "$DOCS_DIR"/*.md; do
        [ -f "$file" ] || continue
        filename=$(basename "$file")
        curl -sf -X PUT \
          "$SUPABASE_URL/storage/v1/object/documentation/admin/$MODULE_FOLDER/$filename" \
          -H "Authorization: Bearer $SUPABASE_SERVICE_KEY" \
          -H "Content-Type: text/markdown" \
          --data-binary "@$file"
        echo "Synced $filename → admin/$MODULE_FOLDER/$filename"
      done
    fi
  env:
    SUPABASE_URL: ${{ secrets.SUPABASE_URL }}
    SUPABASE_SERVICE_KEY: ${{ secrets.SUPABASE_SERVICE_KEY }}
```

**Trigger condition:** The `paths:` trigger in each module workflow already watches `modules/{module-name}/**` — adding `docs/*.md` changes to that path means docs pushes automatically trigger the sync without any extra workflow file.

**In-app editor path:** Admin with `docs.manage` saves directly to Storage from the browser — immediate, no CI needed.

## Best Practices

### Documentation
1. **Docs live next to the code they describe.** Each module's `docs/` folder is the authoritative source. Authors who change a feature also update the relevant `.md` file in the same PR.
2. **Storage as the CDN.** Never serve docs from the built bundle. Supabase Storage is the runtime source — the app just fetches and renders.
3. **DB as the index, not the content.** `admin.documentation_guides` only stores metadata (title, file_name, module, sort_order). The `.md` content stays in Storage.
4. **In-app editor for hotfixes.** When a doc needs a quick correction that doesn't warrant a full PR, the admin editor writes directly to Storage. The next CI push will overwrite with the source-of-truth version from the repo — so critical fixes should also be committed to the repo.
5. **Target roles on guides.** Use the `target_roles` column to surface role-specific guides first (e.g. a `support_admin` sees support-relevant guides prominently).

### Testing
6. **Don't duplicate v6.0.** The Playwright suite and DB tables are the source of truth for automated runs. The Testing Centre UI reads those same tables — it does not maintain a separate store.
7. **Evidence for failures only.** Playwright captures screenshots on failure automatically. Manual evidence uploads are for edge cases and manual session testing. Don't over-engineer capture for passing tests.
8. **Diagnostics are a first alert, not a monitor.** The Diagnostic Centre is run on-demand before a release or after an incident. For continuous monitoring, use your existing Supabase health dashboards.
9. **Defects flow through one system.** All bugs — whether found by Playwright, by testers, or by admins — live in `public.bugs` (v67). The Testing Centre adds a `linked_test_run_id` to create a connection, not a parallel bug tracker.
10. **Test coverage is a guide, not a target.** The coverage report shows which admin pages/RPCs have at least one test case. Aim for critical paths first (auth, permissions, subscriptions) before chasing 100%.
